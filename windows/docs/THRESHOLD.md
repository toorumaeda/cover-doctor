# しきい値（70）の再測定 — Windows 版の画像処理

Mac 版は、実機の画像の 167 組（同じ絵柄）と 164 組（別の絵柄）で、dHash の距離を測り、**同じ絵柄は最大 55、別の絵柄は最小 93** だったので、しきい値を 70 にした。Windows 版は画像の縮小方法が違うので、測り直した。

## Windows 版の作り
- 画像の読み込みと JPEG 化は SkiaSharp。
- dHash の 17×16 への縮小は、**自前の面積平均**（`Imaging.AreaAverageGray`）。OS の画像処理を使わないので、Windows と開発機（Linux）で同じ入力から同じハッシュになる（Wine 上の Windows 版 `CoverDoctor.exe compare` と Linux 版の結果が一致することを確認）。
- 灰色化は 0.299R + 0.587G + 0.114B。透明部分は白の上に置いたものとして扱う。
- Mac 版と同じく、dHash では EXIF の向きを反映しない（JPEG 化のときは反映する）。

## 合成画像での測定（2026-10-18、`tools/measure_threshold.py`、60 枚 × 11 通りの変形）

変形: 長辺 1200/600/300/150 への縮小、JPEG 品質 25/50/95、PNG 化、端を 2%・4% 切り落とし、曲から取り出したときと同じ JPEG 化（アプリのコード）。

| 画像の種類 | 同じ絵柄の最大距離 | 別の絵柄の最小距離（同じ種類どうし） |
|---|---|---|
| 写真に近い画像（ぼかした色の分布＋文字） | **53**（端 4% 切り落とし） | **101** |
| ブロック模様（テストの fixture と同系統） | 66（端 4% 切り落とし） | 44 |
| 細い斜めの縞 | 127（端 4% 切り落とし） | 82 |
| ほぼ一色の背景・グラデーション＋小さな文字 | 40 以下 | 4〜36 |

**写真に近い画像では、同じ絵柄が最大 53、別の絵柄が最小 97〜101 で、Mac 版の実測（55 / 93）とほぼ同じ分布**になった。縮小・再圧縮・PNG 化だけなら、どの種類でも 40 以下。

外れたのは、作り物らしい2つの場合:
1. **細かい縞模様を端から 4% 切り落とす**と、縞の位置がずれて「別」と判定される（距離 127）。実際のジャケットで、曲の画像と iPhone の画像の切り抜きがここまで違うことは、Mac の実測にはなかった。結果は「直せる」になり、曲の画像で上書きされる（見た目は同じ絵柄なので、害は小さい）。
2. **ほぼ一色の画像どうし**（黒地に小さな文字など）は、別の絵柄でも「同じ」と判定されうる（距離 4〜36）。dHash は明暗の差を見るので、平らな画像では差が出にくい。アルバムでは「正しい」と判定されて**触らない**ので、安全な側の誤り。プレイリストでは、「どれとも違う」画像が、ほぼ一色の別アルバムと「同じ」と判定されて「誤り」と扱われる可能性がわずかにある（Mac 版と同じ規則のため、規則は変えていない）。

## 結論
- しきい値 70 は、Windows 版の画像処理でも、写真に近い画像では Mac 版と同じ余裕（両側に 15 以上）がある。**今は 70 のまま**にしている。
- 実機の画像での再測定は、まだ。実機の診断のあとに `CoverDoctor.exe report` を実行すると、距離の分布（アルバム名は出さない）が `report.txt` に出る。Mac の実測で1組もなかった **56〜92 の範囲に入る件数**が 0 に近ければ、しきい値は妥当。多ければ、組ごとに見て決める（相談のうえで）。
